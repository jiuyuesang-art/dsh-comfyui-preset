# 显存与性能策略

> 本机现实（2026-10-05 实测）：**RTX 5070 / 11.91 GB 显存，空闲仅 7.95 GB**（约 4 GB 被占）；
> **RAM 128 GB（空闲 79 GB）**。显存是**唯一稀缺资源**，内存很宽裕 —— 策略要围着这个不对称来做。

---

## 0. 铁律：跑重任务前**必须**查显存

```powershell
# ① 先查
mcp__comfymcp__system_stats          # 看 devices[].vram_free

# ② 不够就清（不会打断正在跑的任务，排队生效）
mcp__comfymcp__free_memory           # unload_models + 清执行器缓存

# ③ 再查确认
mcp__comfymcp__system_stats
```

**阈值参考**（低于这个就别硬上）：

| 任务 | 建议 vram_free |
|---|---|
| Qwen Image 2.1 GGUF Q6_K 出图 | ≥ **6 GB** |
| MiniMax H3 视频（Q4_K_M） | ≥ **8 GB** |
| 同时挂多个模型（如 Edit + 参考图多张） | ≥ **9 GB** |

> ⚠️ `free_memory` **不会打断正在跑的任务** —— 它排队等 worker 下一次迭代才生效。
> 想真正停下任务用 `job action="cancel"`。
> ⚠️ 它**也管不了别的进程**占的显存（本地 LLM 运行时、浏览器硬件加速等）——
> 那种情况只能**告诉用户**，由用户关掉。

## 1. 分层策略：**重模型进显存，轻模型留内存**

这是本机最划算的优化 —— **内存有 79 GB 空闲，显存只有 8 GB**。

**做法：在节点上把轻量模型的 `device` 设成 `cpu`。**

实测确认：`CLIPLoader` 有 `device` 槽位，枚举是 `default` / `cpu`：

```
list_workflow_slots → { "address": "3.device", "enum": ["default","cpu"] }
set_workflow_slot   → "3.device" = "cpu"
```

| 组件 | 放哪 | 理由 |
|---|---|---|
| **UNet / DiT 本体**（生图、生视频的主模型） | 🔴 **显存** | 每一步都要过它，放内存会慢到不可用 |
| **文本编码器**（`qwen3vl_8b` / `qwen3vl_32b` 等） | ✅ **内存（`device=cpu`）** | **只在开头跑一次**，之后不再用 —— 白占显存最不划算 |
| **VAE** | 视情况 | 体积小，通常留显存；显存紧张时可外移 |
| **加速 LoRA** | 显存（跟随主模型） | 体积小、影响大 |

**顺序很重要**：文本编码 → 采样 → VAE 解码。文本编码器用完就可以走，
但 ComfyUI 默认会把它留在显存里**占着不放** —— 这正是"跑前 7.95 GB 却仍 OOM"的常见原因。

> 更彻底的做法是启动参数 `--lowvram` / `--novram`，但那会影响**所有**工作流，
> 需要重启 ComfyUI（`restart_comfyui`）。**优先用节点级 `device=cpu`**，粒度更细、不用重启。

## 2. 加速 LoRA：**先出预览版，再定稿**

**本机已经装好了这些加速 LoRA**（实测扫盘，在 `models/loras/`）：

| 文件 | 用途 | 备注 |
|---|---|---|
| `Qwen-Image-Edit-2509-Lightning-4steps-V1.0-bf16.safetensors` | **Qwen 图像编辑 → 4 步** | 改图预览首选 |
| `minimax_h3_turbo_8step_v1.0.safetensors` | **H3 视频 → 8 步** | 312 MB，最轻 |
| `minimax_h3_ref2v_turbo_4step_v0.1_comfyui_bf16.safetensors` | **H3 参考转视频 → 4 步** | 1.87 GB |
| `lightx2v_I2V_14B_480p_cfg_step_distill_rank64_bf16.safetensors` | 图生视频蒸馏 | 704 MB |
| `turbo8_lora_step2500.safetensors` | 通用 turbo | 1.3 GB |

**工作流（两步走）**：

```
① 预览版：挂加速 LoRA，步数降到 4–8，分辨率可降一档
   → 目的：**快速确认构图 / 姿势 / 角色对不对**
   → 这时不要纠结细节质量

② 定稿版：卸掉加速 LoRA（或降权重），回到正常步数（Qwen 25 步）
   → 参数从预览版继承，只提步数
```

> ⚠️ **加速 LoRA 会改变画风与细节**，预览版的"好不好看"**不能代表定稿版**。
> 它的价值是**快速验证构图与角色身份**，不是最终质量。
> ⚠️ 挂 LoRA 时**权重**与**触发词**要按该 LoRA 的说明来；不确定就先小权重试。

## 3. 时间预算与降级阶梯

**开跑前先估一句**（写给你自己看，也告诉用户）：

| 任务 | 粗估（本机 5070 12 GB） |
|---|---|
| Qwen 2.1 出图 25 步 | 数十秒级 |
| Qwen 2.1 + 加速 LoRA 4 步 | 秒级 |
| H3 视频 5 秒（蒸馏步数） | 分钟级 |
| H3 视频 15 秒（完整步数） | 明显更久，且**成功率未验证** |

**超预算时的降级阶梯**（从上往下试，别一次降到底）：

```
① 挂加速 LoRA + 降步数        ← 只影响质量，不影响构图验证
② 降分辨率 / 缩短时长
③ 减少参考图数量
④ 换更小量化的权重
⑤ 仍然不行 → 🔴 停下问用户（见 §4）
```

## 4. 🔴 硬约束无法达标时：**停下问人，不要凭感觉继续**

这条比任何优化都重要。**"凭感觉继续"会烧掉整轮 token，还产出不可用的东西。**

**必须停下问用户的信号**：

- 显存**清理后仍不足**（`free_memory` 后 `vram_free` 仍低于 §0 阈值）
- 工作流**校验不通过**，且缺的节点/模型**本机没有**
- 需要的模型**下载不了**（官方站与镜像站都失败，见 `comfyui-mcp-ops` 的下载章节）
- **找不到参考图**，而任务又要求角色一致性（见 `comfyui-prompt-craft` §1.5）
- 同一次任务**连续失败两次**以上，且原因不明
- 任务规模明显超出本机能力（如要出 15 秒高分辨率视频）

**停下时要给用户的**（不是一句"失败了"）：

1. **卡在哪**（具体到显存数字 / 缺哪个节点 / 哪个站不可达）
2. **已经试过什么**
3. **2–3 个可选方案**，各带代价（降规格 / 换模型 / 等用户开代理 / 放弃）
4. **你的建议**，但**决定权在用户**

> 这条与 `comfyui-review` 的"采纳权在人"是同一个原则：
> **模型负责把选项摆清楚，不负责替用户拍板。**
