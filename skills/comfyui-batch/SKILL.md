# 批量渲染（一次跑完 N 项）

## 什么时候用 / 什么时候别用

**用**：同一次任务要出 **≥2 项** —— N 个提示词变体、一组镜头、一组种子、图 + 视频混合。

**别用**（走 `comfyui-mcp-ops` 的单任务流程）：
- 只有 1 项 —— **脚本会直接拒绝**（`BATCH_FAILED ... 只有 1 项`，退出码 2），除非显式 `-AllowSingle`
- 还在定下工作流 / 调参数（先调通一张，再批量）
- 🔴 **单独精修一个镜头**（反复看效果、改一处再跑一张、盯着一张调）—— 这是**迭代**，
  每张都要你看过才决定下一步，**不要**塞进批次。批量是「一次定稿、跑完再看」的工具，
  不是「边跑边改」的工具。

## 为什么（这是省 token 的关键）

逐张走「提交 → 等 → 唤醒 → 取图」：**N 项 = N 次唤醒 + N 轮上下文重建**。
批次走「一个脚本跑完」：**N 项 = 1 次唤醒**。

模型侧的动作只有三步，**不要在里面加第 4 次工具调用**：

```
① 写计划 JSON
② 干跑验证    batch-render.ps1 -PlanPath … -DryRun
③ 后台跑一次  run_in_background: batch-render.ps1 -PlanPath … [-OutDir …]
   → 立刻结束本轮，什么都不做      ← 🔴 见下「三条硬约束」
   → 被唤醒时，读末行 +（需要细节再读）报告
```

## 🔴 三条硬约束

1. **不要逐项提交、不要中途追问进度**。起完 `run_in_background` 就**结束本轮**：
   **禁止** `job_output` 轮询、禁止查 `/queue`、禁止给上游发 interrupt。
   批次跑完前，模型**不该被唤醒、不该产生任何 turn** —— 这是省 token 的全部意义。
   进度是给**人**看的（桌面状态栏），不是给模型看的。
2. **等待机制不变**。每项仍由 `wait-job.ps1` 阻塞在 ComfyUI 的 WebSocket 上：事件驱动、**不设超时**。
   批次跑几十分钟（视频更久）是正常的。
3. **提交前必须干跑**。`-DryRun` 会提前暴露：节点地址写错、工作流路径不存在、名字重复、单项。
   这些在提交后才发现，就是白等一轮。

## 桌面状态栏（给人看的）

批次会写 `<计划名>.progress.json`，并拉起一个置顶小窗显示：

```
已完成 1 / 3      [■■■□□□□□]  33%
正在重启 ComfyUI（换进程，显存归零）…
成功 1 · 失败 0 · 总耗时 00:01:03
```

要点：

- **只读状态文件**，不参与渲染；`-NoProgressWindow` 关掉。
- 批次结束它**不会自动关**，停在「全部完成 / 部分失败」上供你回看（Esc 或关闭按钮退出）。
- 它和模型的上下文**完全无关** —— 模型醒来只读末行和报告，不看这个文件。

## 显存：每项之间换一个进程

**默认**：每项之间**重启 ComfyUI**（`tools/comfy-restart.ps1`）。为什么不是只 `/free`：
`/free` 之后显存往往回不到初始值（碎片 / CUDA 上下文 / 缓存分配器各留一点），
**换进程**才能让下一个任务的主模型**整块吃下显存**。实测：重启后可用显存回到 `10.8 GB`（12GB 卡）。

- 启动器自动推断（EasyManager 布局：`<安装根>\start_latest.ps1`），推断不到会让显式传
  `-RestartCommand '<同步命令>'`；**都对不上就明确报错，不瞎启动**。
- 重启约 35–40 秒（大模型更久）—— 这是「用时间换整块显存」，比 OOM 重跑便宜。
- 重启失败会**自动退回 `/free`** 继续跑，不会毁掉整批。
- `-NoRestart`：不重启，只 `/free`（显存富余时更快）。
- 外部管理器（EasyManager 的 comfy.exe）若自己把进程拉起来，脚本会**直接采用新进程**，不会重复启动。

## 产物

- 不给 `-OutDir`：只记录文件名，产物仍在 ComfyUI 的 output 目录。
- 给 `-OutDir`：每项产物**下载**到该目录，文件名前缀项名（`shot0010_a__xxx.png`），不会互相覆盖。
- **不要再用 `fetch_outputs` 逐项搬运** —— 那正是本脚本替你省掉的往返。

## 计划文件

最小可用：

```json
{
  "workflow": "02_env/workflows/qwen21_t2i.json",
  "seedAddress": "7.seed",
  "seedBase": 1000,
  "seedStep": 1,
  "items": [
    { "name": "shot0010_a", "params": { "6.text": "……", "9.filename_prefix": "shot0010_a" } },
    { "name": "shot0010_b", "params": { "6.text": "……" } }
  ]
}
```

- `params` 的键是 **`"<节点id>.<输入名>"`**，值原样写进工作流 —— 不做任何猜测、不做变量替换。
- `seedBase`/`seedStep`：第 i 项的种子 = `seedBase + (i-1) * seedStep`，**只在 params 没自己写种子时生效**。
- 每项可单独覆盖 `workflow`（同一批混跑不同工作流）。
- 完整字段、多工作流、视频示例 → `references/plan-format.md`。

**节点 id 从哪来**：打开工作流 JSON（API 格式）里的数字键。MCP 的 `run_workflow` 用的也是同一份文件。

## 结果怎么读

末行（机器可读，**先读它**）：

```
BATCH_DONE	ok=3	fail=0	total=412.3s	out=C:\…\30_key	report=C:\…\plan.result.json
```

`BATCH_DONE` 全成功 / `BATCH_PARTIAL` 有失败但跑完了 / `BATCH_FAILED` 全失败。
退出码同义：`0 / 1 / 2`；批次被中止（重启没回来）是 `3`。

进程里还会打印每项一行（`✅ name DONE 137.9s`），**但被唤醒后不需要重读日志** ——
需要逐项细节（prompt_id、参数留痕、错误文本、产物清单）时，读报告：

```json
{ "ok": 3, "failed": 0, "total": 3, "totalSeconds": 412.3,
  "items": [ { "name": "shot0010_a", "status": "DONE", "seconds": 137.9,
               "promptId": "…", "files": ["out_A_00001_.png"], "saved": ["C:\\…"], "error": null } ] }
```

## 失败怎么办

- **默认不中断**：某项失败 → 记下来 → 继续跑剩下的 → 最后 `BATCH_PARTIAL`。
  单项失败通常是个例（提示词被拒、某模型 OOM），不该毁掉整批。
- `-StopOnError`：任何一项失败就停（后面的项标记 `SKIPPED`）。**用于失败会连锁的场景**（例如共享同一个显存吃紧的模型）。
- **不要自动重跑失败项**。先读 `error` 字段判断：参数问题改参数、OOM 降分辨率（默认已每项重启），
  然后**只把失败项写进新计划**重跑。

## 常见坑

| 现象 | 原因 / 怎么办 |
|---|---|
| `BATCH_FAILED 计划解析失败：工作流里没有节点 99` | `params` 地址写错。干跑就能发现。 |
| `BATCH_FAILED 只有 1 项` | 单项别走批量（护栏）。改走单任务流程；确需批量加 `-AllowSingle`。 |
| `名字重复` | `items[].name` 必须唯一，否则产物前缀会撞。 |
| 提交就报「工作流校验失败」 | 工作流本身缺输入 / 模型文件名不对。先用单任务流程调通一张。 |
| 每项都很慢（比单张慢） | 正常：默认每项之间**换进程**，要重新加载模型。批次赢的是**唤醒次数**，不是单张速度。 |
| 重启失败（`RESTART_FAILED no-launcher`） | 推断不到启动器。传 `-RestartCommand '<你的启动脚本>'`，或 `-NoRestart` 退回只 `/free`。 |
| 中途 OOM | 已经是每项重启了还 OOM → 降分辨率/步数；或该项单独跑一次定位。 |

- 工作流怎么搭、参数怎么填、MCP 工具怎么用 → `comfyui-mcp-ops`
